## What changed (files and why)

All paths are under `apps/mercato/src/modules/dealer_onboarding/`.

**Gap 5**
- `encryption.ts`: the map `entityId` was `dealer_onboarding:dealer_profiles` (plural). The generator registers `DealerProfile` as `dealer_onboarding:dealer_profile` (singular; see `.mercato/generated/entities.ids.generated.ts`), and the encryption service matches `encryption_maps.entity_id` exactly. The map therefore never applied. It now uses `DEALER_PROFILE_ENTITY_ID`.
- `lib/applicationReview.ts` (new): `findApplicationForReview(em, tenantId, applicationId)`. It loads the profile with `findOneWithDecryption(em, DealerProfile, {id, tenantId, deletedAt:null}, undefined, {tenantId, organizationId:null})` and the documents with a filter that now includes `tenantId` (before, only the profile id was used).
- `api/admin/dealers/applications/[id]/route.ts`: now uses the helper. The shifted-argument call is gone, and so is the `organizationId: id` (profile id) scope.

**Gap 6**
- `commands/shared.ts`: new `resolveKycAttachmentId(document)`. It returns the lower-cased attachment UUID, or throws the same `404 Document not found` as an unknown document. It never passes a non-UUID key to storage.
- `api/dealer/onboarding/documents/[id]/file/route.ts` and `api/admin/dealers/applications/[id]/documents/[documentId]/file/route.ts`: both now call `resolveKycAttachmentId` before `attachmentService.readScoped`. The existing `expectedOwner`, `expectedPartitionCode: 'privateAttachments'` and `requirePrivatePartition: true` checks are unchanged.

**Gap 7**
- `lib/registrationTarget.ts` (new) holds the eligibility rules:
  - `evaluateRegistrationOrganization` is a pure function: the org must exist, not be deleted, have a tenant, have `isActive !== false`, have `parentId == null`, and not be a dealer org.
  - `resolveRegistrationTarget` loads the org through an injected loader. Only if the org is otherwise eligible does it look for any `dealer_profiles` row (live or soft-deleted) for that org within the org's own tenant. Per ADR-003, such a row is what marks a dealer org.
- `api/dealer/onboarding/register/route.ts`: uses the helper. All rejection reasons collapse into the existing response, `404 {"error":"Marketplace organization not found","code":"org_not_found"}`, which the dealer portal already handles. The request and response shapes, rate limit (5/h) and invite-link format are unchanged. The OpenAPI description is updated.

## Decisions made and reasoning

1. **Gap 5: I fixed the read rather than adding a dual-read fallback, because the "scope" never selected key material.**
   - In Open Mercato 0.8.0 the data-encryption key is **per tenant**. `organizationId` only selects which `encryption_maps` row (which fields) applies, with fallback order (tenant, org) → (tenant, NULL) → (NULL, NULL).
   - On **write**, the ORM subscriber (`TenantEncryptionSubscriber.beforeCreate/beforeUpdate`) always uses the row's own `tenant_id` / `organization_id`. For a DealerProfile that is the dealer's own org. Both register (`de.createOrmEntity`) and resubmit (mutate and flush) go through it.
   - On **read**, `findWithDecryption`'s fifth argument is only a fallback for rows **without** scope columns. DealerProfile always has both (NOT NULL), so reads also use the dealer's own org, the same as writes. The `{organizationId: <profile id>}` scope could never have been used, and the route crashed earlier anyway.
   - Nothing on this branch changes which ciphertext can be decrypted, so no existing data can be orphaned and no fallback is needed.
   - The helper passes the trusted tenant and `organizationId: null`. It never invents an org: not the profile id, and not the reviewer's org.
2. **The `entityId` typo fix is inert until a map row exists**, so it is safe to ship. Runtime resolves the entity id from generated metadata, not from `encryption.ts`, which only feeds map seeding. Any row a human seeded under the old plural id never matched anything.
3. **I deliberately did NOT add a migration or upgrade action to activate encryption.** It would switch on encryption for new writes in the shared DB as soon as `yarn db:migrate` runs. That depends on the KMS key configuration (see Risks), which is a key-management decision for you.
4. **Gap 6: I kept `storageKey` in API responses** (admin detail and dealer status) to avoid an API-contract change. It is now an opaque attachment id that is useless without a session matching the dealer's scope. Removing it from the responses is an optional follow-up; neither the admin UI nor the dealer portal reads it.
5. **Gap 7: "root org" is checked as `parentId == null`**, matching CLAUDE.md and `docs/architecture.md` §7.0 (`?organizationId=<root-org-id>`, root org `5e4fe2d8-…`). Dealer orgs are also root orgs once approved and active, which is why the dealer-profile check is the one that matters. Pending dealer orgs are additionally `isActive: false`.

## Gap 7 risk assessment and the stronger option (for you to decide)

**Real risk today:** low to moderate, and not mainly about org ids.
- Org ids are random UUIDs, the endpoint is limited to 5 requests per hour per IP, and the tenant resolved is the only one that exists. Enumerating org ids is not practical.
- The real weakness: the invite "secret" is the root org id. It is permanent, cannot be revoked and is not per-invitee, and it is written in committed docs (`CLAUDE.md`, `docs/architecture.md`). In practice, anyone who sees the link can self-register as many times as the rate limit allows.
- Each registration creates an inactive org and a `dealer:owner` user, and sends an invite email to **any address the caller types in**. That makes it usable for email abuse via the platform's mail sender.
- Each registration can also upload up to 3 × 10 MB of KYC files (20 uploads per hour).
- Admin KYC approval is still the real gate before a dealer can do business.
- Separately, `409 emailAlreadyRegistered` on this unauthenticated route lets anyone check whether an email is registered. Fixing it changes the dealer portal's UX, so it is not changed here.

**Stronger option: admin-issued, single-use, expiring invite tokens (recommended)**
- New entity `DealerInvite` in `dealer_onboarding` (hand-written migration needed) with columns:
  - `id`, `tenant_id`, `organization_id` (the issuing marketplace org)
  - `token_hash` (sha256 of a 32-byte random token, unique; the raw token is never stored)
  - `email` (optional; if set, the registration email must match, case-insensitive)
  - `expires_at` (default 7 days), `max_uses` (default 1), `used_count`, `revoked_at`
  - `created_by`, `created_at`, `deleted_at`
- Admin API, gated by `dealer_onboarding.admin`:
  - `POST /admin/dealers/invites` with `{email?, expiresInDays?}` returns `{id, url}`, where the URL is `https://<dealer-portal>/onboarding/register?invite=<token>`. The raw token is shown once only.
  - `GET /admin/dealers/invites` lists invites.
  - `POST /admin/dealers/invites/:id/revoke` revokes one.
  - Add a small admin UI page.
- Register accepts `inviteToken`. The server hashes it and claims a use with a single atomic statement inside the registration transaction: `UPDATE dealer_invites SET used_count = used_count + 1 WHERE token_hash = ? AND revoked_at IS NULL AND expires_at > now() AND used_count < max_uses RETURNING tenant_id, organization_id, email`. No row returned means the same uniform 404. The tenant comes from the invite and never from client input.
- Migration path, with no flag day:
  1. Ship tokens alongside the existing `organizationId` links, behind `DEALER_REGISTER_ALLOW_ORG_LINK` (default `true`).
  2. Make the dealer portal prefer `?invite=`.
  3. Re-issue the links that are in use.
  4. Set the flag to `false` and drop `organizationId` from the schema.
- Alternative: stateless HMAC-signed tokens, `base64url({tenantId, orgId, exp, email?, nonce}).hmac` with the secret in SSM. There is no table, but there is also no revocation or single-use without a nonce denylist, which needs a table anyway. **Recommendation:** use the DB-backed tokens. Invite volume is low, and revocation, single use and auditability are what's missing today.
- Estimated effort: about a day including tests and admin UI. It needs a product decision on invite lifetime, single use vs multiple uses, and email binding.

## Actions the human must take

1. **Check whether GSTIN/PAN are encrypted in the dev DB.** These are read-only queries:
   ```sql
   select entity_id, tenant_id, organization_id, is_active
     from encryption_maps where entity_id like 'dealer_onboarding:%' and deleted_at is null;
   select count(*) as total,
          count(*) filter (where gstin like '%:v1') as gstin_ciphertext,
          count(*) filter (where pan like '%:v1')   as pan_ciphertext
     from dealer_profiles;
   ```
   Expected result: no map row for `dealer_onboarding:dealer_profile`, and zero ciphertext rows. That means GSTIN/PAN are stored as plaintext today.
2. **Before enabling encryption, confirm the production key setup.** Check that `TENANT_DATA_ENCRYPTION=yes` and that a real key or Vault is configured in SSM (`/giftory/dev/…`), not the `.env.example` dev fallback key (`TENANT_DATA_ENCRYPTION_FALLBACK_KEY`). Data encrypted under a key that later changes becomes unreadable.
3. **Then enable it**, after this branch is deployed. Use a targeted, tenant-wide map for this entity only. Do **not** run `mercato entities seed-encryption --tenant <id>` without `--org`: that also seeds a tenant-wide `auth:user` map (with `email_hash`), which could change how already-plaintext dealer-user emails are looked up at login.
   ```sql
   insert into encryption_maps (id, entity_id, tenant_id, organization_id, fields_json, is_active, created_at, updated_at)
   select gen_random_uuid(), 'dealer_onboarding:dealer_profile', t.id, null,
          '[{"field":"gstin"},{"field":"pan"}]'::jsonb, true, now(), now()
     from tenants t
    where not exists (select 1 from encryption_maps m
                       where m.entity_id = 'dealer_onboarding:dealer_profile'
                         and m.tenant_id = t.id and m.organization_id is null and m.deleted_at is null);
   ```
   Restart or redeploy the backend afterwards; map lookups are cached, including a 5-minute miss cache. New registrations and resubmissions are then encrypted. Existing plaintext rows stay readable, because decrypt leaves non-ciphertext values as they are; a test proves this.
4. **Encrypt the existing rows:** `yarn mercato entities rotate-encryption-key --tenant <tenantId> --dry-run`, review the output, then run it again without `--dry-run`. With a tenant-wide map, this command walks every org in the tenant and encrypts the plaintext values the map covers. Then re-run the query from step 1 to confirm.
5. **Decide on gap 7's invite tokens** (above), and whether the `409` email-exists response on the unauthenticated register route is acceptable.
6. Optionally, review the broader observation under Risks: other modules' data in dealer orgs is probably not encrypted either.

## Risks

- **I could not verify anything at runtime against a real DB or deployment**, as instructed. The claims that the admin detail route currently 500s and that GSTIN/PAN are plaintext come from reading the Open Mercato 0.8.0 source (`shared/lib/encryption/{find,subscriber,tenantDataEncryptionService,entityIds}.ts`, the MikroORM 7 `MetadataStorage`). They are corroborated by the baseline `tsc` error at `[id]/route.ts(29,5)`. Verify with the SQL in step 1 and by opening an application in the admin UI.
- **Root-org check.** If an existing invite link points at a child org, or the root org is somehow `is_active=false`, that link would now get `404 org_not_found`. The documented link uses root org `5e4fe2d8-71a6-4c15-978a-e31df68d84c7`; check that it is root and active: `select id, parent_id, is_active from organizations where id = '5e4fe2d8-71a6-4c15-978a-e31df68d84c7';`
- **Platform-wide encryption gap (observed, not fixed, out of scope).** Open Mercato seeds module encryption maps only for (tenant, setup/root org). Every dealer gets its own organization, so records written in dealer orgs by other modules are probably also plaintext at rest. Examples: dealer users' `auth:user` `email`/`name`, and `audit_logs` snapshots, which include GSTIN/PAN via `serializeDealerProfile` in `commands/shared.ts` for review and resubmit. This deserves its own decision; see step 3 for why a blanket tenant-wide seed is not a safe one-liner.
- **Register rate limit.** It is keyed per client IP. Registrations arrive through the dealer-portal BFF, which forwards `X-Forwarded-For`. If the backend's trusted-proxy depth isn't configured, every dealer shares one bucket of 5 per hour. This is not changed here.
