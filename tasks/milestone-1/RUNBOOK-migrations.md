# Runbook — apply the three Phase 2 migrations to the shared dev database

Written by WS-E (Milestone 1 overnight run, 2026-11-23). Nothing in this runbook has been run
against the shared dev database: the agents had no access to it, by design. Every step below
**was** rehearsed against throwaway local Postgres 17.5 databases (the same major version as
Supabase), set up to look like each state the dev database could be in. The results are in
[WS-E-migrations-isolation-e2e.md](WS-E-migrations-isolation-e2e.md).

**Time needed:** about 20 minutes, most of it reading output. The migrations themselves take
a few seconds. They only create three empty tables and relax one `NOT NULL`.

---

## 0. What is being applied, and why it matters

| Module | Migration (name recorded in `mikro_orm_migrations_<module>`) | What it does |
|---|---|---|
| `dealer_onboarding` | `Migration20261013232854_dealer_onboarding` | `CREATE TABLE dealer_profiles`, `dealer_kyc_documents` + 3 indexes |
| `dealer_org_rbac` | `Migration20261013232900_dealer_org_rbac` | `CREATE TABLE dealer_capabilities` + 1 index |
| `payouts` | `Migration20261020123600_payouts` | `ALTER TABLE dealer_ledger_entries ALTER COLUMN created_by DROP NOT NULL` |

All three are already on `main`, so the backend running on ECS already depends on them. Until
they are applied:

- dealer registration, KYC upload and capability setup fail with `relation "dealer_profiles" does not exist`;
- every system-generated `commission_earned` ledger credit fails on the `created_by NOT NULL` constraint.

The deploy pipeline does **not** run migrations. The ECS container command is `yarn start`, which
runs `mercato server start` with no migrate step. Every schema change therefore needs a person to
run `yarn db:migrate`.

### Review verdict (details in the handoff file)

- **Correct against the entities.** A schema-diff of each module's `data/entities.ts` against
  the database the migrations produced shows **no drift** for `dealer_onboarding` or
  `dealer_org_rbac`. For `payouts` the only difference is cosmetic: the DB has
  `created_at DEFAULT now()` and the entity doesn't declare it.
- **Money columns:** none of the three new tables holds money. `dealer_ledger_entries.amount` is
  `numeric(18,0)` and is not touched. (Separate finding: the `commissions` **entity** declares
  `subtotal_amount`/`commission_amount` as `integer` while the table is `numeric(18,0)`. The next
  `yarn db:generate` will propose `ALTER ... TYPE int` for both columns. **Never accept that hunk.**)
- **Not idempotent:** the two `CREATE TABLE` migrations have no `IF NOT EXISTS`. If the tables
  were ever created without the migration being recorded, `yarn db:migrate` stops with
  `relation "dealer_kyc_documents" already exists`. Step 2 detects this case and §5 fixes it.
  The `payouts` `ALTER ... DROP NOT NULL` is naturally idempotent.
- **No `down()`** in the two `CREATE TABLE` migrations, so rollback is manual SQL (§6).
- Each migration runs in its own transaction. A failure rolls that migration back completely
  (verified). Modules run in alphabetical order, so modules that come before the failing one
  stay applied. That is safe: re-running continues where it stopped.

### What state is the dev database probably in?

Evidence in the repo:

- P2-UI-17 ran a read-only query in mid-October. At that point `dealer_profiles`,
  `dealer_kyc_documents` and `dealer_capabilities` did **not** exist on the dev DB.
  `dealer_order_assignments`, `commission_rules`, `order_commission_snapshots` and
  `dealer_ledger_entries` **did** exist, each with its tracking table.
- On 2026-10-20, `payouts` Migration20261020123600 was generated by diffing against the live
  dev DB, which means `created_by` was still `NOT NULL` that day.
- Also on 2026-10-20, commit `c29372e` says "a real file upload through the app now lands in
  S3" on the deployed backend. If that was a KYC upload, someone created the dealer tables
  after mid-October, probably by running `yarn db:migrate` by hand.

So the dev DB is most likely in one of these states. Step 2 tells you which one:

| State | What you will see in step 2 | Action |
|---|---|---|
| **A — never applied** (most likely) | dealer tables absent, no tracking rows, `created_by` NOT NULL | §4 apply, normal path |
| **B — already applied by hand** | dealer tables present **and** tracking rows present | the lister shows 0 or 1 pending; §4 just finishes |
| **C — tables exist, not recorded** | dealer tables present, tracking table missing or empty | §5 baseline, **then** §4 |
| **D — shape mismatch** | Q3 shows anything other than `ok` | **stop**; see §5.3 |

## 2. Read-only pre-checks (run all of these first)

### 2a. SQL: paste into the Supabase SQL editor, one query at a time

The Supabase SQL editor only shows the result of the **last** statement, so run each block
separately. All five are plain `SELECT`s.

**Q1: do the Phase 2 tables and tracking tables exist, and how many rows do they hold?**

```sql
select t.name as relation,
       to_regclass('public.' || t.name) is not null as exists,
       case when to_regclass('public.' || t.name) is not null
            then (xpath('/row/n/text()', query_to_xml(format('select count(*) as n from public.%I', t.name), false, true, '')))[1]::text::bigint
       end as row_count
from (values ('dealer_profiles'), ('dealer_kyc_documents'), ('dealer_capabilities'),
             ('dealer_order_assignments'), ('commission_rules'), ('order_commission_snapshots'),
             ('dealer_ledger_entries'),
             ('mikro_orm_migrations_dealer_onboarding'), ('mikro_orm_migrations_dealer_org_rbac'),
             ('mikro_orm_migrations_dealer_orders'), ('mikro_orm_migrations_commissions'),
             ('mikro_orm_migrations_payouts')) as t(name)
order by 1;
```

**Q2: which Phase 2 migrations are recorded as applied?**

select m.module,

**Q5: do the dealer roles exist in each tenant, and do they have their Phase 2 permissions?**
This is not a migration concern, but if it is wrong the dealer flows still fail after migrating.
The `dealer:owner`/`dealer:staff` roles are only created when a tenant is created
(`onTenantCreated`) or by `mercato init`. A dev tenant created before these modules existed
won't have them.

```sql
select t.name as tenant_name, want.name as role, r.id is not null as role_exists,
       coalesce((select string_agg(f, ', ' order by f) from jsonb_array_elements_text(a.features_json) f
                 where f ~ '^(dealer_|commissions|payouts)'), '') as phase2_features
from tenants t
cross join (values ('admin'), ('dealer:owner'), ('dealer:staff')) as want(name)
left join roles r on r.tenant_id = t.id and r.name = want.name and r.deleted_at is null
left join role_acls a on a.role_id = r.id and a.deleted_at is null
where t.deleted_at is null
order by 1, 2;
```

Expected after everything is fixed: `admin` has `commissions.manage, commissions.view,
dealer_onboarding.admin, dealer_orders.manage, dealer_orders.view, dealer_org.admin,
payouts.manage, payouts.view`. `dealer:owner` has 8 features, `dealer:staff` has 3. See §7 if
they don't.

### 2b. List exactly what `yarn db:migrate` would apply (read-only script)

`yarn db:migrate` applies every pending migration of every module, not just these three, and
MikroORM's own "pending" check creates missing tracking tables (a write). The script below
lists pending migrations using only `SELECT`s inside a `READ ONLY` transaction. Postgres itself
rejects any write.

Save it as `%TEMP%\list-pending-migrations.mjs`. Keep it outside the repo so it never gets
committed:

```js
// READ-ONLY: lists the migrations `yarn db:migrate` would apply, per module, without
// touching the schema. Unlike MikroORM's own getPending(), this never creates the
// mikro_orm_migrations_<module> tracking tables. Every query runs inside a
// READ ONLY transaction, so Postgres itself rejects any accidental write.
// Run from apps/mercato:  node <path>/list-pending-migrations.mjs
import fs from 'node:fs'
import path from 'node:path'
import { createRequire } from 'node:module'
import { pathToFileURL } from 'node:url'

const appDir = process.cwd()
const require = createRequire(path.join(appDir, 'package.json'))
const { createResolver } = await import(
  pathToFileURL(path.join(appDir, 'node_modules/@open-mercato/cli/dist/lib/resolver.js')).href
)
const { Client } = require('pg')

if (!process.env.DATABASE_URL && fs.existsSync(path.join(appDir, '.env'))) {
  // Same source `yarn db:migrate` uses: apps/mercato/.env (never overrides an exported value).
  require('dotenv').config({ path: path.join(appDir, '.env'), quiet: true })
}
const url = process.env.DATABASE_URL
if (!url) {
  console.error('DATABASE_URL is not set')
  process.exit(2)
}
const isLocal = /@(localhost|127\.0\.0\.1)[:/]/.test(url)
const client = new Client({ connectionString: url, ssl: isLocal ? undefined : { rejectUnauthorized: false } })

const resolver = createResolver(appDir)
const modules = resolver.loadEnabledModules().slice().sort((a, b) => a.id.localeCompare(b.id))

function migrationsDir(entry) {
  const roots = resolver.getModulePaths(entry)
  if (entry.from === '@app') return path.join(roots.appBase, 'migrations')
  return path.join(roots.pkgBase.replace(/[/\\]src[/\\]modules[/\\]/, '/dist/modules/'), 'migrations')
}

await client.connect()
let totalPending = 0
try {
  await client.query('BEGIN TRANSACTION READ ONLY')
  for (const entry of modules) {
    const dir = migrationsDir(entry)
    if (!fs.existsSync(dir)) continue
    const files = fs
      .readdirSync(dir)
      .filter((f) => /^Migration.*\.(ts|js)$/.test(f) && !f.endsWith('.d.ts'))
      .map((f) => f.replace(/\.(ts|js)$/, ''))
      .sort()
    if (!files.length) continue
    const table = `mikro_orm_migrations_${entry.id.replace(/[^a-z0-9_]/gi, '_')}`
    const exists = (await client.query('select to_regclass($1) as t', [`public.${table}`])).rows[0].t !== null
    const executed = exists
      ? new Set((await client.query(`select name from "${table}"`)).rows.map((r) => r.name))
      : new Set()
    const pending = files.filter((f) => !executed.has(f))
    const unknown = [...executed].filter((n) => !files.includes(n))
    totalPending += pending.length
    if (pending.length || unknown.length) {
      console.log(`${entry.id}${exists ? '' : '  (tracking table does not exist yet)'}`)
      for (const p of pending) console.log(`   PENDING                ${p}`)
      for (const u of unknown) console.log(`   RECORDED, NO FILE      ${u}`)
    }
  }
} finally {
  await client.query('ROLLBACK').catch(() => {})
  await client.end()
}
console.log(`\nTotal pending: ${totalPending}`)
```

Run it (Git Bash):

```bash
cd apps/mercato
node "$TEMP/list-pending-migrations.mjs"
```

**Expected output for state A** (this is the actual output from the rehearsal against a copy

   PENDING                Migration20261013232854_dealer_onboarding

payouts

- **Anything else listed as PENDING** (another `@app` module like `storefront`/`gift_catalog`,

- **`RECORDED, NO FILE`** means the DB has a migration this checkout doesn't know about

## 3. Backup

Take both of these:

1. **Supabase snapshot:** Dashboard → Project → Database → Backups. Confirm a backup from the
   last 24 h exists (or Point-in-Time Recovery is enabled). Write down its timestamp.
2. **Your own dump** (needs `pg_dump` 17 or newer; the Supabase server is PG 17). Use the
   **direct** connection string:

   ```bash
   pg_dump "$DIRECT_DATABASE_URL" --format=custom --no-owner --no-privileges \
     --file "giftory-dev-before-phase2-migrations-$(date +%Y%m%d-%H%M).dump"
   ```

   If the whole DB is too large, at least dump the schema plus the affected tables:

   ```bash
   pg_dump "$DIRECT_DATABASE_URL" --schema-only --no-owner -f giftory-dev-schema-before.sql
   pg_dump "$DIRECT_DATABASE_URL" --data-only --no-owner -t dealer_ledger_entries \
     -t 'mikro_orm_migrations_*' -f giftory-dev-affected-data-before.sql
   ```

   Do not commit the dump. It contains customer PII.

## 5. If `yarn db:migrate` fails with `relation "…" already exists` (state C)

This means the tables exist but the migration was never recorded. The failing migration's
transaction was rolled back, so nothing is half-applied. Modules alphabetically after the
failing one (for example `payouts`) were **not** attempted yet.

1. Run **Q3**. Every row must say `ok`. If any row says `MISSING`, `EXTRA` or `DIFFERENT`, go
   to 5.3.
2. Record the migration as applied ("baseline" it). Run only the lines for the tables that
   already exist:

   ```sql
   begin;
   -- dealer_onboarding (dealer_profiles + dealer_kyc_documents already exist)
   create table if not exists mikro_orm_migrations_dealer_onboarding (
     id serial primary key, name varchar(255), executed_at timestamptz default current_timestamp);
   insert into mikro_orm_migrations_dealer_onboarding (name)
     select 'Migration20261013232854_dealer_onboarding'
     where not exists (select 1 from mikro_orm_migrations_dealer_onboarding
                       where name = 'Migration20261013232854_dealer_onboarding');
   -- dealer_org_rbac (dealer_capabilities already exists)
   create table if not exists mikro_orm_migrations_dealer_org_rbac (
     id serial primary key, name varchar(255), executed_at timestamptz default current_timestamp);
   insert into mikro_orm_migrations_dealer_org_rbac (name)
     select 'Migration20261013232900_dealer_org_rbac'
     where not exists (select 1 from mikro_orm_migrations_dealer_org_rbac
                       where name = 'Migration20261013232900_dealer_org_rbac');
   commit;
   ```

   Also check the indexes exist. If any are missing, create them. These are the exact
   statements from the migration:

   ```sql
   select indexname from pg_indexes where tablename in ('dealer_profiles','dealer_kyc_documents','dealer_capabilities') order by 1;
   -- expected: dealer_cap_profile_idx, dealer_capabilities_pkey, dealer_kyc_docs_profile_idx,
   --           dealer_kyc_documents_pkey, dealer_profiles_pkey, dealer_profiles_scope_idx, dealer_profiles_status_idx
   create index if not exists "dealer_kyc_docs_profile_idx" on "dealer_kyc_documents" ("dealer_profile_id", "document_type", "deleted_at");
   create index if not exists "dealer_profiles_status_idx" on "dealer_profiles" ("tenant_id", "kyc_status");
   create index if not exists "dealer_profiles_scope_idx" on "dealer_profiles" ("tenant_id", "organization_id", "deleted_at");
   create index if not exists "dealer_cap_profile_idx" on "dealer_capabilities" ("dealer_profile_id", "tenant_id", "deleted_at");
   ```

3. Re-run the lister (2b), then `yarn db:migrate` (§4). The rehearsal of exactly this
   sequence finished with `payouts: 1 migration applied` and exit code 0.

### 5.3 Shape mismatch (state D)

Do not baseline. The existing table was created by something other than this migration. If the
table is **empty** (Q1 `row_count = 0`), the simplest fix is to drop it and let the migration
create it:

```sql
drop table dealer_capabilities;
```

Use the matching table name, and only after the backup. If it holds data, write a one-off
reconciliation migration that `ALTER`s it to the expected shape, then baseline. Ask before
doing this.

### Other failures

- **SSL / connection / timeout:** check `DATABASE_URL`, use the direct connection, retry. Nothing was applied.
- **Lock timeout on `dealer_ledger_entries`:** the `ALTER` needs a brief exclusive lock. Retry
  when the backend is idle (it scales to zero after 30 minutes).
- **Any other error:** each migration is its own transaction, so the failing one left nothing
  behind. Run the lister to see what did apply, fix the cause, and re-run. Do not edit the
  migration files; they are shipped.

## 6. Verify

1. Lister (2b) → `Total pending: 0`.
2. Q1 → the three tables exist. Q2 → the three names recorded. Q3 → every row `ok`.

3. Q5 → roles and permissions present (otherwise §7).
4. Functional smoke test, optional but recommended. On the deployed admin, open

## 7. Dealer roles / permissions missing (Q5)

These are writes. Run them only if Q5 shows a problem.

- **Role exists but `phase2_features` is empty or partial:** run the idempotent ACL sync.
  It only adds missing features:

  ```bash
  cd apps/mercato && yarn mercato auth sync-role-acls
  ```

- **`dealer:owner` / `dealer:staff` missing for a tenant:** create the roles, then run the sync
  above. Rehearsed: this restored 8/3 features per tenant.

  ```sql
  insert into roles (id, name, tenant_id, created_at)
  select gen_random_uuid(), r.name, t.id, now()
  from tenants t
  cross join (values ('dealer:owner'), ('dealer:staff')) as r(name)
  where t.deleted_at is null
    and not exists (select 1 from roles x where x.tenant_id = t.id and x.name = r.name and x.deleted_at is null);
  ```

## 8. Rollback notes

Prefer rolling **forward**. The deployed code already expects these tables and the nullable
column, so rolling back breaks the deployed backend again.

- **`payouts` `created_by` nullable:** do not roll back. Its `down()`
  (`SET NOT NULL`) fails as soon as any system-generated ledger credit exists, and it would
  re-break every commission credit.
- **`dealer_onboarding` / `dealer_org_rbac`:** these have no `down()`. Manual rollback is only
  sensible if the tables are still **empty** (Q1). Rehearsed; afterwards the lister shows the
  two migrations as pending again:

  ```sql
  begin;
  drop table if exists dealer_capabilities;
  drop table if exists dealer_kyc_documents;
  drop table if exists dealer_profiles;
  delete from mikro_orm_migrations_dealer_org_rbac  where name = 'Migration20261013232900_dealer_org_rbac';
  delete from mikro_orm_migrations_dealer_onboarding where name = 'Migration20261013232854_dealer_onboarding';
  commit;
  ```

- **Anything worse:** restore the §3 backup (Supabase dashboard restore or
  `pg_restore --clean --no-owner -d "$DIRECT_DATABASE_URL" <file>.dump`).

## 9. Other environments

Repeat steps 2–6 for every database that runs this code (any future staging or production
Supabase project). The deploy pipeline will not do it for you. A cheap safeguard is to run the
lister in CI or before each deploy and fail when `Total pending > 0`.
